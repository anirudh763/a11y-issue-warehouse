Android accessibility issues on GitHub

Issues from 15 open-source Android apps, collected from the GitHub search API on 2026-11-11. Titles, labels, dates and links only; authors and issue bodies are not shown.

The accessibility-issue sample is a set of weak labels, not human ground truth, and not only bugs (it includes feature requests). It is selected by labels and keywords, not checked by hand: an issue is in it if it carries the app's accessibility label, or if the keyword search returned it and its title or body contains talkback, screen reader, accessibility or a11y. Some are therefore only loosely about accessibility, such as release notes or test failures that mention a11y.

    Keyword leakage: what happens when the search words are removed

    Most issues in the accessibility sample are in it because they contain one of the four search words (talkback, screen reader, accessibility, a11y). A rule that looks for those words scores itself against its own definition. The repository's classifier test (analysis/classify.py, leave-one-repository-out over 2,477 issues) measured F1 with the words left in and with them masked out of the text.

With the words removed the keyword rule finds nothing, while a model trained on the other repositories still reaches the F1 shown for an unseen repository and finds 71.1% of the 114 issues that maintainers labelled as accessibility but that contain no search word. It does not show that the model detects accessibility problems in general: nobody verified the labels, and the interval treats issues as independent although they are not.

    About the data

    What it can show

    • Which issues the GitHub search API returned on 2026-11-11 for each app's accessibility label (13 apps have one) and for the query talkback OR "screen reader" OR accessibility OR a11y.
    • A comparison sample from the same apps: for every calendar month that had at least one result from the label or keyword query, the oldest issues created that month, as many as that month had label and keyword results. That size was set before the 180 unrelated keyword hits were removed, which is why the comparison sample (1,290) is larger than the accessibility sample (1,187).
    • Each issue's state, labels, open and close dates and comment count as of the collection date.
    • Why each issue is in its sample: which queries returned it and which search words its title or body contains.

    What it cannot show

    • All accessibility issues. The search index matches whole words, so "accessible" or "screen-reader" alone does not match. Counts mean "issues this search found".
    • Verified labels. Nothing was hand-labelled, and comparison issues are not checked negatives.
    • Pooled trends free of one app. mozilla-mobile/fenix contributes 583 of the 1,187 accessibility-sample issues (49.1%) and 1,159 of the 2,643 loaded issues (43.9%), and is archived, so all of its issues are closed.
    • Why an issue was closed. "Closed" includes not-planned, duplicate and stale-bot closures. Reopen history is not available.
    • Apps without a label. duckduckgo/Android and home-assistant/android have no accessibility label by this method, so only keyword hits represent them.

    The excluded sample

    GitHub returned 180 issues for the keyword query that contain none of the four words; all contain "screen" and "reader" separately, mostly from the Reader feature of WordPress and WooCommerce. They are not counted as accessibility issues. 166 of them are in no analysis and appear here under "Excluded keyword hits"; the rest were also drawn by the comparison sample.

    Ownership and privacy

    Issue titles belong to the people who filed them on GitHub. This explorer shows titles, labels, dates and links to the original issues, never author names, avatars or issue bodies. To have an issue removed from this copy, open an issue in the repository. Details: DATA.md, README limitations.
