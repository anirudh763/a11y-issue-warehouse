      How the samples are built
      
          
      15 open-source Android apps; GitHub Search API snapshot from 2026-11-11. Only titles, labels, dates and links are included.
      
          
      Accessibility candidates are weak labels, not human ground truth; the sample includes feature requests and unrelated matches. Selection is by the app's accessibility label or a keyword-query result containing TalkBack, screen reader, accessibility or a11y in its title/body.
      
          
      The comparison sample takes the oldest issues by month, matched to the monthly label/keyword result count. The target size was set before 180 unrelated keyword hits were removed, so it contains 1,290 issues versus 1,187 accessibility candidates.
      
          
      Excluded keyword hits
      
          
      180 hits contained "screen" and "reader" separately but none of the four search terms. They are excluded from accessibility candidates; 166 are excluded from all analyses.
      
        
      

        
      
          
      What it can and cannot show
      
          
      
            
      
              
      What it can show
      
              
        
                
      • Which issues the GitHub search API returned on 2026-11-11 for each app's accessibility label (13 apps have one) and for the query talkback OR "screen reader" OR accessibility OR a11y.
        • 
                
      • Each issue's state, labels, open and close dates and comment count as of the collection date.
        • 
                
      • Why each issue is in its sample: which queries returned it and which search words its title or body contains.
        • 
              
      
            
      
            
      
              
      What it cannot show
      
              
        
                
      • All accessibility issues. The search index matches whole words, so "accessible" or "screen-reader" alone does not match. Counts mean "issues this search found".
        • 
                
      • Verified labels. Nothing was hand-labelled, and comparison issues are not checked negatives.
        • 
                
      • Pooled trends free of one app. mozilla-mobile/fenix contributes 583 of the 1,187 accessibility-sample issues (49.1%) and 1,159 of the 2,643 loaded issues (43.9%), and is archived, so all of its issues are closed.
        • 
                
      • Why an issue was closed. "Closed" includes not-planned, duplicate and stale-bot closures. Reopen history is not available.
        • 
                
      • Apps without a label. duckduckgo/Android and home-assistant/android have no accessibility label by this method, so only keyword hits represent them.
        • 
              
      
            
      
          
      
        
      

        
      
          
      Keyword leakage: what happens when the search words are removed
      
          
      Most accessibility candidates contain the same search words used to select them. A classifier using those words can score against the sample definition. The leave-one-repository-out test (analysis/classify.py, 2,477 issues) compares raw and masked text.
      
          
          
      
            
      
              Classifier results, all held-out repositories pooled
              
      SystemTextPrecisionRecallF1F1 95% intervalRecall on label-only positives
      
              
            
      
          
      
          
      With search words masked, the keyword rule finds none; the model finds 71.1% of 114 label-only positives. This does not establish general accessibility detection: labels are unverified, and the interval treats dependent issues as independent.
      
        
      

        
      
          
      Pipeline and checks
      
          
      The explorer reads data/issues.json, exported from an offline SQLite warehouse built from committed raw search pages:
      
          
        
            
      1. make load builds data/warehouse.db from data/raw/ offline.
        2. 
            
      2. make check runs schema and data-quality checks; the known two-word "screen reader" match is reported.
        3. 
            
      3. make site-check checks the browser export against the warehouse.
        4. 
            
      4. make e2e compares filter counts and manifest IDs with SQL.
        5. 
          
      
          
      If the data file is missing or malformed, every screen says so and the downloads stay disabled; nothing is shown from a partial file.
      
        
      

        
      
          
      Ownership and privacy
      
          
      Titles belong to their GitHub authors. This copy shows titles, labels, dates and source links; bodies, author names and avatars are excluded. Request removal · Data details · Limitations.
      
          
      AI-assisted (Claude). Automated axe checks only; no manual screen-reader test.
